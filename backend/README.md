# Шпаргалка по бекенду и Fastify


## Архитектура файлов

- `src/` содержит код приложения, который используется при его запуске и работе в рантайме.
- Вспомогательные файлы находятся за пределами `src/`: например, отдельные скрипты в `scripts/` и миграции базы данных в `drizzle/`.


## Точка входа

`src/main.ts` — точка входа приложения. В ней только настройка Fastify: создание экземпляра сервера, подключение плагинов и запуск. Остальная логика находится в других файлах.


## Вспомогательные скрипты

Скрипты в `scripts/` не участвуют в работе приложения. Если скрипту нужен Fastify, он создаёт отдельный экземпляр и подключает необходимые плагины и маршруты. Экземпляр из `src/main.ts` не импортируем: этот файл запускает сервер.


## Плагины Fastify

Код внутри `src/` желательно оформлять как плагины Fastify. Обычные модули тоже допустимы, но для частей приложения, которые подключаются к серверу, предпочтительны плагины.

Плагины лучше регистрировать плоско: на одном уровне, без вложения одного плагина раздела приложения в другой.

Исключение — маршруты. `src/routes/api.routes.ts` собирает плагины маршрутов и задаёт им префиксы. Общий `apiRoutes` можно подключать как в приложении, так и во вспомогательных скриптах (например, для генерации OpenAPI и вывода дерева маршрутов).

Например, `drizzlePlugin` создаёт подключение к базе, добавляет `server.drizzle` через декоратор и закрывает соединение в хуке `onClose`. Обёртка `fastify-plugin` делает декоратор доступным другим плагинам; поэтому в `main.ts` плагин базы регистрируется до маршрутов.


## Зависимости и контекст запроса

Всё, что относится к конкретному запросу, держи в его контексте. Зависимость оформляй как плагин, когда её нужно связать с инфраструктурой Fastify: жизненным циклом сервера, хуками или декораторами. Простые библиотеки используй напрямую: например, ради `hash` и `verify` из `argon2` отдельный плагин и DI не нужны.


## Разделы API

Каждый раздел API находится в отдельной папке внутри `src/routes/`:

- `routes.ts` описывает контракт API: пути, методы, схемы запросов и ответов. Это своеобразный контроллер раздела.
- `handlers.ts` содержит обработчики запросов.
- `schemas.ts` хранит вынесенные схемы и типы раздела.

Если фронтенду нужен прямой контракт, а не тип, сгенерированный из OpenAPI, его можно вынести в `shared/contracts` и использовать с обеих сторон.


## Пути API

Планируем плоское API: каждый ресурс имеет свой раздел и префикс, без вложения одной сущности в путь другой. Внутри раздела маршруты описывают операции над его ресурсом — например, `/`, `/search`, `/me` и `/:id` с нужными HTTP-методами.

Пример путей из раздела пользователей:

```ts
server.get("/", ...);
server.get("/search", ...);
server.get("/me", ...);
server.get("/:id", ...);
server.put("/:id", ...);
server.patch("/:id", ...);
server.delete("/:id", ...);
```


## Схема маршрута

В `schema` указываем только поля, нужные конкретному маршруту:

```ts
schema: {
  // Описание операции для OpenAPI.
  operationId: "operationName",
  summary: "Short summary",
  description: "Detailed description",
  tags: ["section"],

  // Схемы входных данных для проверки запроса.
  body: bodyJsonSchema,
  querystring: queryJsonSchema,
  params: paramsJsonSchema,
  headers: headersJsonSchema,

  // Схемы ответов по HTTP-статусам для сериализации.
  response: {
    200: responseJsonSchema,
    400: { $ref: "HttpError" },
  },

  // Дополнительные настройки OpenAPI.
  hide: false,
  deprecated: false,
  consumes: ["application/json"],
  produces: ["application/json"],
  externalDocs: { url: "https://example.com/docs" },
  security: [{ bearerAuth: [] }],
}
```

Valibot используем для описания схем. Через `toJsonSchema` преобразуем их в JSON Schema, которую Fastify применяет для проверки входных данных и сериализации ответов:

```ts
body: toJsonSchema(requestSchema, {
  typeMode: "input",
  errorMode: "throw",
}),
response: {
  200: toJsonSchema(responseSchema, {
    typeMode: "output",
    errorMode: "throw",
  }),
  400: { $ref: "HttpError" },
},
```

`errorMode: "throw"` нужен, чтобы при преобразовании не потерять незаметно логику валидации из Valibot-схемы. Если проверку можно выразить в JSON Schema, используем её в Fastify. Если нельзя преобразовать без потерь, проверяем данные напрямую Valibot. Не делим одну проверку на два последовательных прохода ради предполагаемого выигрыша в скорости.


## Документирование ответов

В `response` явно перечисляем все HTTP-статусы, которые может вернуть маршрут, включая ошибки. Если хендлер вернёт, например, `403`, но схема его не описывает, сгенерированный клиент не узнает об этом статусе и не сможет корректно учесть его в типах.


## Обработка ошибок

На уровне хендлера роута ошибки делим на ожидаемые и неожиданные.

Неожиданные ошибки, а также любые ошибки, которые мы явно не обработали, доверяем стандартному обработчику Fastify. Поэтому в общем случае блок `try/catch` в хендлере излишен. Fastify логирует ошибку и формирует ответ. Для ошибки без HTTP-статуса Fastify возвращает `500`. Исходное сообщение ошибки по умолчанию попадает в ответ клиенту. При необходимости на уровне роута, плагина или сервера можно задать обработчик ошибок, который будет маскировать внутренние сообщения бэкенда.

Ожидаемую ошибку можем сформировать сами: создаем HTTP-ошибку соответствующей утилитой `@fastify/sensible` и выбрасываем ее через `throw`. Например: `throw req.server.httpErrors.unauthorized("Invalid email or password")`. Fastify обработает ее и отправит клиенту заданные HTTP-статус и сообщение.

Может понадобиться дополнительная работа с ошибкой хендлера. Ее можно организовать централизованно: через `onError` для наблюдения за ошибками или обработчик ошибок для их преобразования. Локально используем `try/catch`. При этом следуем тому же подходу EAFP, что и при передаче ошибок Fastify: проще попросить прощения, чем разрешения. Сначала выполняем операцию, а при отказе распознаем ошибку и обрабатываем ее по бизнес-логике. Нераспознанные ошибки повторно выбрасываем без дополнительного логирования. Оборачивать весь хендлер только ради логирования и повторного `throw` не нужно. И `throw` HTTP-ошибки, и reply-хелпер `@fastify/sensible` передают ошибку обработчику Fastify; выбор между ними не отключает стандартное логирование.
